# Executable policy contract

OKF 0.2 requires concept YAML/type. The following producer extension is additionally
required ONLY for deterministic negotiation, not for ordinary OKF consultation:

```yaml
type: Policy
status: published
institution: example-institution
product: example-product
effective_from: "2026-01-01T00:00:00Z"
effective_until: "2027-01-01T00:00:00Z"
negotiation:
  max_installments: 3
  max_discount_percentage: "0"
  offer_discount_percentage: "0"
  payment_types: [cash, installment]
payment:
  methods: [pix, boleto]
  methods_by_payment_type:
    cash: [pix, boleto]
    installment: [boleto]
  delivery_channels: [email]
```

All values above are synthetic examples, NOT authorized commercial policy.
A human must approve real metadata in a draft; RAW cannot promote itself.
Unspecified executable terms block proposals, without blocking knowledge reads.
Existing prose-only bundles remain readable but cannot authorize financial offers.

The tool checks published/current metadata, institution/product, a read receipt
and snapshot/hash. Transactional eligibility can narrow, never enlarge policy.
Account amounts stay outside OKF. Money and percentages travel as decimal strings.
`offer_discount_percentage` is the exact creditor-owned discount used by the
transactional tool and must not exceed `max_discount_percentage`. The customer
does not supply or override it.
`methods_by_payment_type` is mandatory and prevents a method allowed for one
payment type from being reused for another.
The returned cent-balanced schedule sums exactly to the negotiated total.

Confirmation is a NEW actual HumanMessage with CONFIRMAR ACORDO and the exact
offer ID, generated by a human-approved UI button or typed by the user. The
LLM's explicit_confirmation argument alone cannot create an agreement.
This is synthetic identity verification, not a production KYC mechanism.

## Discounts by overdue range (Runtime 0.13.4)

Instead of `negotiation.offer_discount_percentage`, a policy can declare
`negotiation.discount_tiers`. Never supply both. Example synthetic table:

```yaml
negotiation:
  max_installments: 1
  max_discount_percentage: "10"
  payment_types: [cash]
  discount_tiers:
    - min_days_overdue: 0
      max_days_overdue: 30
      offer_discount_percentage: "5"
    - min_days_overdue: 31
      max_days_overdue: 90
      offer_discount_percentage: "8"
    - min_days_overdue: 91
      max_days_overdue: 180
      offer_discount_percentage: "10"
    - min_days_overdue: 181
      max_days_overdue: null
      offer_discount_percentage: "10"
```

Ranges are inclusive, ordered, contiguous starting at zero, and the last must
have no upper bound (`null`). All percentages must respect the policy ceiling;
malformed rows, gaps, overlaps and ambiguous fixed-plus-tier definitions reject
the proposal. The selected tier also caps discounts passed by internal callers.

Only backend `fixture.debt.days_overdue` (a nonnegative integer) or its ISO
`due_date` supplies the age. A missing day count is calculated from the due date
using the server date, consistent with customer lookup. Invalid or missing debt
context blocks the action; neither a customer statement nor LLM arguments can
supply a day count or a discount. Existing fixed-percentage policies continue to
work. Creating an offer fixes its discount and amount; crossing an increasing
tier boundary does not reprice an existing agreement during payment validation.

Deploy the Runtime before publishing a tier policy. Older runtimes cannot execute
it. Rollback activates the previous OKF bundle before restoring the old Runtime;
sessions already pinned to tier policies require the compatible Runtime.
